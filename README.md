# he-uav-mapping

Database and web dashboard for a systematic mapping study on homomorphic encryption (HE) in unmanned aerial vehicles (UAVs): applications, schemes, and costs.

## About the study

This repository supports the systematic mapping study *Homomorphic encryption in unmanned aerial vehicles: a systematic mapping of applications, schemes, and costs*, developed as part of a direct PhD at ICMC-USP (Instituto de Ciências Matemáticas e de Computação, Universidade de São Paulo).

The data extracted from each primary study answers seven research questions:

| RQ | Topic |
| --- | --- |
| RQ1 | Research type |
| RQ2 | UAV application and problem addressed |
| RQ3 | HE schemes, libraries, and parameters |
| RQ4 | Validation approach |
| RQ5 | Where and when each HE operation runs (location and flight phase) |
| RQ6 | Reported costs and baselines |
| RQ7 | Threat model: adversaries, their behavior, and protected data |

The extraction data is loaded into a relational database and explored through a web dashboard.

## Data model

The model was designed in two steps, following the extended entity-relationship notation (ME-RX) and the ER-to-relational mapping algorithm.

- **Conceptual model:** [`docs/er/MSL_DER.drawio`](docs/er/MSL_DER.drawio). `Study` sits at the center, and each RQ is a colored region of the diagram.
- **Relational model:** [`docs/relational/`](docs/relational/). It has 27 tables and 27 foreign keys:

| Group | Tables |
| --- | --- |
| Study | `Study`, `StudyAuthor` |
| RQ1 | `ClassifiedAs`, `ResearchType` |
| RQ2 | `Addresses`, `UAVApplication` |
| RQ3 | `SchemeAdoption`, `PlainTextEncode`, `HEScheme`, `Library` |
| RQ4 | `ValidatedBy`, `ValidationApproach` |
| RQ5 | `OperationExecution`, `ExecutedAt`, `HEOperation`, `Location`, `Phase` |
| RQ6 | `Reports`, `ComparesWith`, `CostType`, `BaselineType` |
| RQ7 | `Encrypts`, `AdversaryModel`, `AdversaryBehavior`, `Targets`, `DataCategory`, `AdversaryParty` |

Each option list from the extraction form is a catalog table (for example, `ResearchType` or `Location`), so a study can only be linked to valid options.

## Getting started

The database and the dashboard run in Docker, so you do not need to install PostgreSQL or Python.

Requirements: [Docker](https://docs.docker.com/get-docker/) with Docker Compose. On Windows, use Docker Desktop with the WSL 2 backend.

1. Create your local settings file and set a password:

   ```bash
   cp .env.example .env
   ```

2. Start the database and the dashboard:

   ```bash
   docker compose up -d --build
   ```

   On the first start, the database container runs the scripts in `db/` in numeric order: `01_create_tables.sql` creates the 27 tables, `02_populate_catalogs.sql` fills the catalog tables with the options of the extraction form, `03_triggers.sql` adds the integrity rules that span several tables, `04_populate_studies.sql` loads the studies and `05_views.sql` creates the views. The dashboard starts once the database is ready. `--build` is only needed the first time and after changing `dashboard/requirements.txt`.

3. Open the dashboard at <http://localhost:8501>. The `dashboard/` folder is mounted into the container, so changes to the code show up after a page refresh.

Integrity rules are enforced at three levels:

- **Single table** (`01_create_tables.sql`): primary keys, foreign keys, `CHECK` and `UNIQUE`.
- **Across tables, row by row** (`03_triggers.sql`): triggers reject a row as soon as it breaks a rule. For example, a study whose HE operations were not executed cannot have a library, a plaintext encoding, or the research type Validation research; and an option that means "nothing else" (such as `Not validated` or `No baseline`) cannot appear together with another option.
- **Across tables, at the end of a load** (`03_triggers.sql`): `VerificaCarga()` checks total participation, such as every study having at least one research type and every adopted scheme having its three HE operations. Called before `COMMIT`, it rolls back the whole load if anything is missing. `SELECT * FROM ViolacoesParticipacao();` lists what is missing.

## Querying the data

The dashboard reads the views in `db/05_views.sql`; the counting logic lives in SQL, not in the front end. A few page-specific queries read the tables directly, also read-only: the zone grouping of RQ5 (`ExecutedAt`), the cost combinations of RQ6 (`Reports`) and the adversary behaviors of RQ7 (`AdversaryBehavior`). Almost every facet is multi-valued (a study can report several costs, schemes or locations), so every count is `COUNT(DISTINCT StudyId)` and percentages within a facet do not add up to 100%. Each count also carries `StudyIds`, the list of studies behind it.

| View | Returns |
| --- | --- |
| `VwStudyFacet` | One row per (study, facet, value): the base of the other views |
| `VwFacetOption` | Every option of every facet, used or not, so empty cells show up as gaps |
| `VwFacetCount` | Number of studies per option |
| `VwFacetCross` | Number of studies for every pair of options (materialized) |
| `VwStudyOverview` | One row per study, with all facets and scheme details as JSON |
| `VwKpi` | Headline numbers |
| `VwOperationFlow`, `VwOperationFlowPattern` | Where each study encrypts, evaluates and decrypts, and how many studies follow each pattern |
| `VwValidationLadder` | Highest validation step reached by each study (not used by the dashboard) |
| `VwReportingMatrix` | Which items each study reports (security level, library version, code, baseline...) |
| `VwSchemeHierarchy` | Family > scheme > library > version |
| `VwThreatMatrix` | Protected data × party × adversary behavior |
| `VwAuthor`, `VwCoAuthorship` | Co-authorship network |

`VwFacetCross` is materialized. After changing the data without recreating the database, run `REFRESH MATERIALIZED VIEW VwFacetCross;`.

No secondary indexes are created. PostgreSQL already indexes every primary key and unique constraint, and every link table's primary key starts with `StudyId`, so the joins in the views are covered. With 37 studies each table fits in a few pages and the planner prefers sequential scans anyway.

## Dashboard

The dashboard is a Streamlit app with a top menu. Every number on it comes from the database at page load, so it always matches the loaded data. Clicking a bar, a bar segment or a matrix cell lists the studies behind the number, with a link to each paper.

| Page | What it shows |
| --- | --- |
| Overview | Headline numbers, studies per year by HE family, and a matrix of where research concentrates (UAV application × an attribute chosen from a list) |
| Studies | Search and filters over all facets; one row per study, and the full extraction of a study in a pop-up window. The filtered table can be downloaded as CSV |
| RQ1 · Research type | Studies per research type |
| RQ2 · UAV applications | Studies per application and which applications appear together |
| RQ3 · HE schemes and libraries | Studies per scheme (colored by family), family > scheme > library, what the studies report about library, version, parameters and security level, and plaintext encodings |
| RQ4 · Validation | Validation approaches split by whether the HE operations were executed, and validation × HE family |
| RQ5 · Where and when HE runs | Location × HE operation, the flow from encryption to decryption between zones (Sankey), repeated full flows, and flight phase |
| RQ6 · Costs and baselines | Reported costs, which costs are reported together (UpSet), baselines, and cost × baseline |
| RQ7 · Threat model | Protected data, adversary parties split by assumed behavior, and protected data × party |

Conventions used on every page:

- Counts are numbers of distinct studies; a study can count in several bars, so bars do not add up to 37.
- Gray marks options that mean "not reported" (`Not reported`, `Not stated`, `No baseline`, `Not validated`).
- Hatching marks HE operations that were proposed but not executed.
- PHE, FHE, SHE and undetermined families keep the same color (blue, green, orange, gray) on every page.
- In the matrices, darker blue means more studies and `·` means no study (a gap).
